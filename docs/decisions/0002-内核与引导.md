# ADR 0002 — 内核与引导链（ZFSBootMenu）

- 状态：已采纳
- 日期：2026-11-14

## 背景

L1 验收要求 ZFS root + 开机可回滚，但 `install.sh` 的 chroot 段在此处留白（TODO）。本 ADR 是这段的施工图，要定四件事：

1. 内核形态（源码 / 二进制）
2. ZBM 获取路径
3. initramfs 职责边界
4. 内核 cmdline 与回滚语义的衔接

架构已定调 **arm64**（`make.conf.example` 的 `-march=armv8.2-a`、`VIDEO_CARDS="virtio virgl"`），L3 x86 真机差异见"后果"。

## 决策

### 1. 内核：`gentoo-kernel-bin`（dist-kernel）+ `zfs-kmod` 同版本构建

- L1 迭代速度优先：bin kernel 免掉内核本身数小时编译；
- `zfs-kmod` 经 dist-kernel 机制对着 `/usr/src/linux-*-gentoo-dist` 的预构建树编译模块；
- 验收 #5 只考 `@system` 编译时间，内核不参与计分；
- L2 binhost 落地后重新评估是否切源码内核（届时编译由 binhost 机器承担）。

### 2. 引导：ZBM 唯一，grub 移出 world

- ZBM 取自 **GURU overlay** 的 `sys-boot/zfsbootmenu`（v3.0.1），保持宪法"一种分发 = Portage"；
- 双引导器并存违反"只有一种正确做法"——world 中的 `sys-boot/grub` 移除；
- fallback（仅当 GURU ebuild 断链时）：上游 release 二进制，**需在此追加记录并显式豁免"一种分发"**。

### 3. ESP 布局与 BE 判定

```
ESP (513MiB, FAT32)
└── /EFI/ZBM/vmlinuz.EFI         # efibootmgr 注册为首选启动项
```

- ZBM 开机自己扫描 pool、列出 BE（"有 kernel + initramfs 的 ZFS 数据集"），
  **没有 grub.cfg 等价物，也无需升级后刷新菜单**；
- 内核与 initramfs **必须放在数据集内的 `/boot`**（不能在独立 ESP 上），
  否则 ZBM 扫不到（VM 实测）；
- ZBM 生成 EFI 需要 UEFI stub：无 systemd 系统用 `sys-apps/systemd-utils[boot]`。

### 3b. 数据集用 `mountpoint=/` + `canmount=noauto`（**2026-11-18 实测修正**）

> 本节在 L1 第一轮曾写作「必须 legacy」，该结论不正确。
> 在干净临时 pool 上实测并复核后确认：
> legacy 不是 OpenZFS 的要求，而是 **fstab 里 zfs 条目**的副作用。

**正确配置：**

```bash
zfs set mountpoint=/       rpool/root/ordo    # 或 legacy 也行，但不是必须
zfs set canmount=noauto    rpool/root/ordo    # BE 模型：不自动挂载
zfs set mountpoint=/home   rpool/home
zfs set canmount=on        rpool/home
```

**fstab 只挂 ESP（到 `/efi`，不是 `/boot`）：**

```
/DEV/vda1   /efi   vfat   defaults   0 0
```

**为什么当年误判为 legacy**：

`root=ZFS=` 的 dracut initramfs 用 `mount -t zfs` 挂根，当时以为"非 legacy 会报
cannot be mounted using 'mount'"。实测发现 dracut 的
`/usr/lib/dracut/modules.d/90zfs/zfs-lib.sh` 明确分了两个分支：

```sh
if [ "${mountpoint}" = "legacy" ] ; then
    mount -t zfs "${dataset}" "${NEWROOT}"
else
    mount -o zfsutil -t zfs "${dataset}" "${NEWROOT}"   # ← 非 legacy 完全支持
fi
```

**真正的元凶**是 `/etc/fstab` 里的这两行：

```
rpool/home    /home   zfs   defaults   0 0
```

它们由 OpenRC 的 `localmount` 用**不带 `zfsutil`** 的 `mount -t zfs` 执行 →
必然失败。而 `zfs-mount` 服务同时在跑 → 双重机制打架。当时改成 legacy
"恰好"绕过了这个冲突，于是被误认为是硬性要求。

**改用 `mountpoint=/` 的收益（一改三得）**：

1. **内核进入 BE 快照** —— 内核在数据集内 `/boot`，回滚时内核一起回退
2. **ZBM 自动发现全部 BE** —— 不再需要 `org.zfsbootmenu:active=on`
   （那个属性只是 legacy 数据集的补丁）
3. **rollback 产生的 clone 天然成为可见 BE**

**代价**：需要干净重装验证（不能在现有 legacy 系统上热改）。

### 3b-bis. `/boot` 绝不挂 ESP（2026-11-18 补）

**ZBM 扫描的是「数据集内的 `/boot`」，不是 ESP。**

如果 fstab 写 `${DISK}1 /boot vfat`，会形成两份分叉的内核：

```
ESP   /boot/vmlinuz-X   ← emerge 更新这里
数据集 /boot/vmlinuz-X   ← ZBM 启动读这里（永不更新）
```

后果：升级内核后 ZBM 仍 kexec 旧内核 + 新 `/lib/modules` → panic。

**正确做法**：ESP 挂 `/efi`，`/boot` 是数据集内的普通目录。

### 3c. 其余实测约束

- `/boot` 必须在 chroot 前挂载，否则 zfs-kmod/zfs 的 postinst 写内核失败
- 内核/initramfs 的 `.old` 变体必须清理，否则 generate-zbm 选错版本
- BE 内核 cmdline 需 `/etc/kernel/cmdline`，含 `console=ttyAMA0,115200`
  （否则启动后串口静默）与 `zfs_force=1`（强制导入）
- `spl_hostid=0`：pool 由 live 环境（hostid=0）创建时需一致
- ZBM 的 `MountPoint` 不能设，否则 generate-zbm 尝试挂载 /boot 失败

### 4. BE initramfs：dracut 生成，必须自含 ZFS

**ZBM 是 kexec 型引导器**：选定 BE 后加载该 BE `/boot` 里的 kernel + initramfs，
追加 cmdline 后移交控制权。它只负责"选"，**不负责"挂"**——

> BE 自己的 initramfs 必须能在 early userspace 导入 pool 并挂上 root。

因此 BE initramfs 由 dracut 生成，包含：

- `zfs-kmod` 内核模块 + `zfs` 用户态工具（dracut zfs 模块）
- `/etc/hostid`（**必须与 pool 创建时的 hostid 一致**，经典翻车点）
- cmdline 固定 `root=ZFS=rpool/root/ordo`（dataset 名由 install.sh 从 `config/dataset` 生成）

### 5. 回滚语义（2026-11-18 实测修正）

> 本节曾写「ZBM 以临时克隆启动快照」与「在线回滚被 ZFS 语义禁止」，两条均不准确。
> 审查者二号核对 ZBM v3.0.1 源码 + 干净 pool 实测后修正如下。

**ZBM 的实际机制**（`snapshot_dispatcher()`，没有"临时克隆启动"这一项）：

| 按键 | 行为 |
|---|---|
| ENTER | `zfs send \| zfs recv` 复制成独立 BE |
| Ctrl+X | `zfs clone` + **`zfs promote`** |
| Ctrl+C | 仅 `zfs clone` |
| Ctrl+R | **原地** `zfs rollback -r`（需输入 ROLLBACK 确认） |
| Ctrl+N | 新建快照 |

**正确的回滚路径**：

```
升级失败
  → 重启进 ZBM
  → 选中当前 BE → Ctrl+S 进快照子菜单
  → 选中 @pre-update-*
  → Ctrl+X（clone and promote）→ 得到可启动的影子系统
  → 启动该影子系统
  → 在其中执行 ordo snap rollback <标签>（或直接用 ordo snap rollback 一步到位）
  → 重启，回到升级前状态
```

**关于"在线回滚"的实测结论**：

`zfs rollback -r` 对**已挂载的根数据集**返回 0 并生效（在干净 pool 上多次复现）。
真实限制**不是**"busy"，而是：

```
cannot rollback to '...': clones of previous snapshots exist
```

即**快照存在 clone 依赖**时才拒绝。

**但 Ordo 仍然要求重启，理由变了**：

- 能执行不等于安全。在线 rollback 会替换运行中系统的文件树，
  进程持有旧 inode、后续加载的 `.so` 可能与已运行的库不匹配。
- BE 的原子性要求「内核 + initramfs + 用户态」一起回退，
  这只有重启才能保证。
- 这与 FreeBSD `bectl`、NixOS generation 的做法一致。

**不做"失败自动回滚"** —— 与 FreeBSD `bectl`、NixOS 同级；
"引导失败计数器自动回滚"留待 L2+。

## 代价（已知并接受）

1. bin kernel 与"源码可控"气质有张力，L1 接受，L2 重新评估；
2. GURU 是用户共同维护的 overlay，ebuild 可能滞后上游 ZBM 版本；
3. dracut initramfs 配置是调试热点：hostid 不一致、模块缺失、
   `root=ZFS=` 拼写错误，都在"起不来"的场景里。

## 后果

- `install.sh` chroot 段按此施工：
  `eselect repository enable guru` → emerge 内核/zfs/zbm → dracut → ESP 写入 + efibootmgr；
- `doctor` 后续增补：ZBM EFI 存在于 ESP、hostid 一致性检查；
- L3 x86 真机差异清单：`-march`、`VIDEO_CARDS` 更换，cmdline 与链路不变；
- 引导链三处一致性（内核版本 = zfs-kmod 版本 = dracut initramfs 内模块版本）
  由 install.sh 顺序保证，升级路径由 `sysup` 的 emerge 事务性保证。
