# ADR 0013 — 阶段 B 准入重估：最小引导链验证

- 状态：提案
- 日期：2026-11-23
- 关联：ADR 0002（内核与引导）、ADR 0012（Apple Silicon M2，阶段 B 准入条件由本篇重估）、deviations #4（zfs 内核上限）、#49（/boot-on-ESP）

## 一、问题陈述

ADR 0012 为阶段 B（裸机）设定了准入条件：**需 ≥60GB 独立分区**，未满足前不进入实施。
2026-11-23 本机实测：内部 APFS 容器未分配 **51.7GB**、Data 卷可用 **48GB**，仍差约 12GB。

但「60GB」这个数是按**完整 @world 安装**估的，而阶段 B 要回答的未知数是另一件事：

> ZFS root + ZFSBootMenu 能否在 m1n1 → U-Boot → ESP 这条链上起来？

这条链的验证**不需要**完整桌面栈，也不需要 60GB。用原准入条件把阶段 B 挡在门外，
等于用「产品安装」的空间指标去拦一个「引导链可行性」实验——指标与问题不匹配。

同时 ADR 0012 与 README 把「外置盘即插即用」当成唯一产品形态。实测这块 512GB 盘
（`Protocol: USB`）后，这一点也需要与引导链分开评估。

## 二、候选评估

| 路线 | 空间需求 | 能回答的问题 | 判定 |
|---|---|---|---|
| A. 维持 ≥60GB，先清盘再整装 | 60GB+ | 产品完整性，但清盘后仍要先撞引导链未知数 | 驳回：把最大未知数排在最后 |
| **B. 内部最小验证（桩 3GB + 根 15GB）** | ~18GB | 引导链四条判据，全部可证伪 | **选定**：启动成本最低，失败可无损回退 |
| C. 直接以外置 USB 盘做根 | 0（内部只桩） | 只在链条已通时才有意义 | 驳回：把两个未知数叠在一起，失败无法归因 |
| D. 停在 UTM VM | 0 | 已答完（阶段 A） | 驳回：VM 的 edk2 ≠ Apple 的 m1n1/U-Boot |

## 三、决定

1. **60GB 准入条件收窄适用范围**：它约束「完整安装」，不约束「引导链最小验证」。
   阶段 B 的最小验证预算为 内部 ~18GB（桩 ~3GB + 最小根 ~15GB），本机 48GB 可满足。
2. 阶段 B 拆成**四条判据阶梯**，每条带证伪方式，任一条不通过即停并登记结论：
   - 判据 0（无硬件）：`sys-fs/zfs` 能否对 `sys-kernel/asahi-sources` 编出内核模块 —— **已通过（2026-11-23，见第五节）**
   - 判据 1（桩装）：U-Boot 能出现并从本 OS 的 ESP 启动 `\EFI\BOOT\BOOTAA64.EFI`
   - 判据 2（核心）：ZBM 在该链上能看到并挂载内部 zpool
   - 判据 3：ZBM 能引导 asahi 内核到 multi-user（Apple DTB 传递）
3. **外置 USB 盘做根：降级并基本否决**。Asahi 官方 FAQ 明确「Apple Silicon hardware does not
   support booting from USB storage, at all」，且 boot picker 从外置盘只能引导 macOS 布局，
   **不能引导外置盘上的 fuOS**。U-Boot 的 `bootcmd_usb0` 是**运行时手动绕过**，只适合当安装介质，
   不适合当日常系统盘。→ README 与 ADR 0012 的「外置便携盘即插即用」形态需另行重估，不得再当前提。
4. 本阶段**不改 `install.sh`**（不加 `--target asahi`）。ADR 0012 原话「先手工最小验证，
   再声明化」保持不变；声明化属阶段 C，且必须等本轮结论。
5. 判据 0 在现有 UTM VM 内完成，不动机器；判据 1 起才涉及内部盘与安全策略。
6. **deviations #49 升为阶段 B 前置修复项**：内核必须落在数据集内 `/boot`（ZBM 的扫描目标），
   ESP 只挂 `/efi`（m1n1 引导对象 + `\EFI\BOOT\BOOTAA64.EFI`）。判据 2 之前必须先修到位，
   否则 ZBM 看不到内核，判据 3 无从开验。
7. **A 路线（镜像安装包）可行性已由参考实现证实，但不在阶段 B 内实施**。`omacom/omarchy-mac-installer`
   是同一路线的成品：fork 的 Asahi engine（钉死 v0.9.2）+ `installer_data.json` 模板 + 单镜像覆盖
   35 个 board + 首启才取身份与加密。其模板与我们读源码推得的结构一致（EFI `source: esp` +
   `copy_firmware`、Boot/Root 为 `image` 裸镜像、Root `expand: true`）。A 路线的实施条件见第八节。
8. **固件是判据 3 的一部分，不是收尾项**：`vendorfw/firmware.cpio` 放在 ESP，必须在 udev 之前进入
   initramfs，否则表现为「能开机、能 ssh、无屏无网」的假绿。判据 3 的验收必须包含内屏点亮与 Wi-Fi。
9. **B 的产出即 A 的素材**：判据 2、3 通过后，机器上已有一份可运行的 Ordo；对它就地打快照、
   裁剪成 `root.img`，比重新设计镜像构建流程可靠。

## 四、后果（好的与坏的）

好的：最大未知数从「装完才知道」变成「18GB 就能知道」；失败回退只删桩装容器，不碰 macOS 数据卷；
判据 0 可在无硬件条件下先淘汰「ZFS 与 asahi 内核不兼容」这个可能让整条路线作废的风险。

坏的：桩装需要把启动安全性降为 Permissive 并进 1TR，属机器级操作且需人工在场；
验证完成后若结论为「需上游支持」，README 的外置盘形态要跟着改；
判据 2 的结论可能受 U-Boot `EFI_BLOCK_IO` 实现限制，届时不是本仓库能修的问题。

## 五、证据

**上游口径（2026-11-23 实取）**

- OS 布局：一个 OS = 一个 APFS 容器分区（约 2.5GB「stub macOS」，含 m1n1 stage2 + DTB + U-Boot）
  + 该 OS 自己的 ESP + root 等分区。来源：`asahilinux.org/docs/platform/open-os-interop`。
  → 根分区默认在内部；「内部只桩、根在外置」不是安装器行为。
- 外置引导：原文「External boot is not supported with the native Apple Silicon boot tooling,
  making U-Boot a hard necessity」；「Booting from a USB」需中断默认脚本并 `bootcmd_usb0` / `usb start` / `usb reset`。
  来源：`asahilinux.org/docs/sw/u-boot`。
- 安全：降级 Permissive Security 只能在 1TR 中做；1TR 只能冷启动长按电源键 + Machine Owner 凭据；
  部分操作需二次输入。来源：`asahilinux.org/docs/platform/security`。
- 机型支持：Mac14,2（MacBook Air 13-inch, 2022）Installer=yes；主显示/键盘/触控板依赖 `linux-asahi`，
  WiFi 6.1、蓝牙 6.2 已上游。来源：`asahilinux.org/docs/platform/feature-support/m2`。

**判据 0 — 已通过（2026-11-23，UTM VM 内存量取证）**

取证方式：停机后以仓库内 Gentoo arm64 minimal ISO 的内核直启（`-kernel`/`-initrd`，绕开图形 grub），
把 VM 的 qcow2 以 `readonly=on` 挂为第二块 virtio 盘，`zpool import -f -N -R /mnt -o readonly=on rpool`
后 `mount -t zfs -o ro rpool/root/ordo /mnt` 读取。全程未写原盘，事后 `zpool export` 并关机。

| 检查项 | 实测 |
|---|---|
| 源码包 | `/var/db/pkg/sys-kernel/asahi-sources-7.0.9_p2` |
| 源码树 | `/usr/src/linux-7.0.9-asahi-2`、`/usr/src/zfs-2.4.4` |
| 模块产物 | `/lib/modules/7.0.9-asahi-2/extra/zfs.ko`、`spl.ko`（模块树 105M） |
| vermagic | `7.0.9-asahi-2 SMP preempt mod_unload aarch64`（与内核完全一致） |
| emerge 记录 | `1795369314 … sys-fs/zfs-2.4.4`，186 秒完成，`exiting successfully` |
| 已安装包 | `sys-fs/zfs-2.4.4`（AUTOCLEAN 已卸旧版） |

版本层面的前置核对同样成立：树内 `asahi-sources` 为 `7.0.9_p2` / `6.19.14_p2`，
而 `zfs 2.4.4` 的 `MODULES_KERNEL_MAX=7.2`（`config/package.mask/l1-zfs-pin`，deviations #4），
`7.0.9 < 7.2`，与实测一致。

同次取证发现两件与阶段 B 直接相关的事：

1. **asahi 内核从未被引导过**：`last -f …/wtmp` 显示每次启动都是 `6.18.63-gentoo-dist-bin`，
   `/var/log` 内无 `7.0.9-asahi` 记录。ESP 上虽已有 `vmlinuz-7.0.9-asahi-2`（42M）、
   `EFI/ZBM/vmlinuz-asahi.EFI`（103M）、`EFI/ZBM/initramfs-7.0.9-asahi.img`（21M）与 `cmdline-asahi`，
   但没有一次成功引导。→ 判据 3 仍完全未验。
2. **deviations #49 在 Asahi 语境下会由黄转红**：该 VM 的内核镜像在 ESP，数据集内 `/boot` 无内核；
   而本设计是 ZBM 扫数据集内 `/boot`。真机上若沿用现状，**ZBM 将看不到 asahi 内核**。
   故 #49 不是历史遗留，而是阶段 B 的前置修复项（见第三节第 6 条）。


**上游口径补录（2026-11-23，第三方调研）**

- **USB 冷启动被物理否决**：Asahi FAQ 原文「Apple Silicon hardware does not support booting from
  USB storage, at all. It is completely physically impossible to boot from USB while making no changes
  to internal storage.」boot picker 从外置盘只能引导 macOS 布局，不能引导外置盘上的 fuOS。
  来源：`asahilinux.org/docs/project/faq`、`/docs/platform/introduction`。
- **官方不推荐整盘镜像安装**：「the disk image installation flow is a curiosity of early bringup work
  that ended up sticking … it is not the way forward for workstation-class hardware」，并列了 9 条要求
  （首启打乱 root 分区 UUID、首启向尾部空闲扩容、镜像 ZIP 且可流式下载、含全部 Asahi 专用包、
  多机型实测等）。来源：`asahilinux.org/docs/alt/policy`。
- **官方推荐给下游发行版的路径**是 fork 安装器 + 自托管 `installer_data.json`，而非自建 ISO。
  同上 policy 与 `github.com/AsahiLinux/asahi-installer`。
- **固件必须早于 udev**：`firmware.cpio` 位于 ESP 的 `vendorfw/`，理想路径是由 bootloader 作为
  early initrd 加载；回退路径是读 `/chosen/asahi,efi-system-partition` 找 ESP，再扫 vfat。
  Linux 侧硬条件：需要固件的驱动必须是模块。来源：`/docs/platform/open-os-interop`。
- **参考实现 `omacom/omarchy-mac-installer`（v2.3.16，已公证）**：
  fork Asahi engine 钉死 v0.9.2；`installer_data.json` 为 EFI 512MB（`source: esp` +
  `copy_firmware` + `copy_installer_data`）、Boot 2GB（`boot.img`）、Root 32GB（`root.img`,
  `expand: true`）；单镜像覆盖 35 个 board；**镜像内固定 UUID**
  （`ROOT_UUID=4f4d5801-…-0001`），首启才取身份并加密磁盘；镜像构建在 aarch64 + Docker，
  约 15 分钟 / 25GB。安装后仍需关机→长按电源键→进 Recovery→认证→跑其 Recovery app 收尾。

**本机基线实测（2026-11-23）**

| 项 | 值 |
|---|---|
| 机型 / 系统 | Mac14,2；macOS 27.2.1；FileVault 已开；SIP enabled |
| 内部盘 | APFS 容器 245.1GB，未分配 51.7GB，Data 可用 48GB |
| 外置 disk6 | 512.1GB，`Protocol: USB`，SSD，固定盘；EFI 209.7MB + 空 APFS「OrdoWork」477GB |
| 外置 disk7 | 63.9GB「CHIPFANCIER」→「OrdoBackup」32GB 已用（备份盘，本流程不碰） |
| 旧 VM 系统盘 | 44.7GB qcow2 存在；`UTM.app` 与 `qemu-system-aarch64` 可用 |

## 六、快速安装路径：binhost（ADR 0003 的落地）

阶段 B 暴露出一个与引导链无关、但会长期拖累体验的问题：**每台新机器都要重新编译整个
`@world`**（clang/llvm 单个 90 分钟以上）。这与 Asahi 桩装的分钟级体验不匹配。
Asahi installer 负责的只是「建容器 + 装 m1n1/U-Boot + 给 ESP」，这部分本来就快；
慢的是 Ordo 自己的安装模型。

ADR 0003 已定案 binhost（`BINHOST=` + `FEATURES=getbinpkg`），但至今未实现，
`config/make.conf.example` 的 `BINHOST=""` 仍为空（deviations #12）。本节把实施路径写死：

1. **一次性构建**：在已装好的 UTM VM 里执行
   `quickpkg --include-config=y @world`，把**已安装**的文件反向收拢为
   `${PKGDIR}/<类别>__<包>-<版本>.gpkg.tar`。`quickpkg` 不需要源码、不重跑编译。
2. **参数一致性（硬约束）**：binpkg 绑定编译时的 `CFLAGS` / `USE` / `CHOST` / `ACCEPT_KEYWORDS`。
   构建机与目标机必须是同一档，否则 Portage 判定不适用并回退重编，下载白费。
   故阶段 C 的 asahi 分支必须**先定死真机的 `-march` 与 `VIDEO_CARDS`**，再据此构建 binhost。
3. **分发**：按 ADR 0003，tag 钉住的 GitHub Releases（immutable URL），rsync 推送 + http 拉取。
4. **效果**：新机安装从「编译 10 小时」降为「下载解包」量级。

**顺序约束**：binhost 不解决引导链问题。判据 2 未通过之前，优化灌装速度没有意义——
灌得再快，起不来的系统仍是起不来。判据 2 的最小系统只需
stage3 + `sys-kernel/asahi-sources` + `sys-fs/zfs` + ZBM，不足 10 个包，不依赖 binhost。

## 七、验证步骤

判据 0（在 UTM VM 内，不动机器）：

```sh
emerge --onlydeps --ask=n sys-kernel/asahi-sources
ls /usr/src/ | grep asahi
# 对 asahi 源码树编译 sys-fs/zfs 的外部模块；modinfo zfs 正常即通过
```

判据 1–3（需人在机器前）：

1. 备份数据到 disk7；Time Machine 跑一次。
2. 冷启动长按电源键进 1TR，认证后在「启动安全性实用工具」把 macOS 容器降为 Permissive Security。
3. 运行 Asahi installer，选 **UEFI environment only**；重启确认 U-Boot 出现（判据 1）。
4. 只手工执行 [install.sh](../../install.sh) 的分区与 zpool 段到内部空闲空间，**不要整跑**
   （`install.sh` 第 100 行的 `mklabel gpt` 是整盘独占语义，用在 Mac 上等于抹机）。
5. 把 ZFSBootMenu 部署到该 OS 自己的 ESP（`\EFI\BOOT\BOOTAA64.EFI`），不用 GRUB。
   确认 ZBM 磁盘列表里出现 `rpool`（判据 2）；再换 `sys-kernel/asahi-sources` 引导到 multi-user（判据 3）。

回退：`diskutil apfs deleteContainer` 删桩装容器；1TR 里恢复 Full Security 与默认启动盘。

## 八、B → A 路线与工作量

B 与 A 不是二选一，是一条流水线：**B 的终点即 A 的原料**。判据 2、3 通过后机器上已有一份
可运行的 Ordo，把它就地快照、裁剪就是 `root.img`；反之先做 A 等于闭眼造镜像。

| 阶段 | 内容 | 验收 | 谁做 | 量级 |
|---|---|---|---|---|
| **B0 准备** | 备份（38G 已完成）、二进制仓（770 包/2.1G 已完成）、内核产物（42M 内核 + 105M 模块 + 21M initramfs，VM 内已编好） | `make check` 全绿 | 已完成 | — |
| **B1 桩装** | 1TR → Permissive → Asahi installer `UEFI environment only`，30GB | U-Boot 出现（判据 1） | 用户在机器前 20 分钟 | 0.5 天含往返 |
| **B2 链条** | 内部建 zpool → ZBM 落 `\EFI\BOOT\BOOTAA64.EFI` → 引导 asahi 内核 | 判据 2、3（含内屏与 Wi-Fi） | 我 + 用户在机器前 | 0.5–1 天 |
| **B3 固化** | 对可用系统打快照，导出为后续镜像的基线 | `zfs send` 可还原 | 我 | 0.5 天 |
| **A1 最小镜像** | `root.img`（ZFS 池）+ `esp/` 树 + `installer_data.json`，本地 `REPO_BASE`，不签名、只本机 | 同一台机用 installer 重装成功 | 我 | 2–4 天 |
| **A2 首启** | 首启取身份、扩池（`zpool online -e`）、可选加密 | 首启后 `ordo doctor` 全绿 | 我 | 1–2 天 |
| **A3 产品化** | 签名公证的 macOS app + 特权 helper + 签名 catalog + 多机型矩阵 + 镜像流水线 | 参考实现同等形态 | — | **3–6 周** |

**「几周」指的是 A3，不是 A1。** A1+A2 大约 **一周内**可以出可用的本地镜像安装；
A3 才需要复刻 `omarchy-mac-installer` 那套（647 个文件、公证、catalog、35 机型验证）。

三条 A 路线的已知技术债，必须在 A1 之前各自有结论：

1. **ZFS 池 GUID 重复**：官方要求首启打乱 root UUID，ZFS 无 `reguid` 等价操作（未确认）。
   单机安装无影响；一旦回到「便携盘」形态就会同机可见两个同 GUID 池。
2. **vendorfw 进 initramfs**：ZFS root 没有「顺手挂 ESP」的便利，回退路径依赖
   `/chosen/asahi,efi-system-partition` 是否被 U-Boot 透传给 ZBM 装载的内核——未验。
3. **ZBM.EFI 走默认路径**：Asahi 文档只提 GRUB / systemd-boot，ZBM 零出现，
   属合理外推，需判据 2 实证。

## 九、与本篇冲突的既有表述（待后续修订）

- README「外置便携盘在桩装过的 M1/M2 之间即插即用」：与 Asahi FAQ 的 USB 冷启动否决冲突，
  且 fuOS 不能从外置盘引导。**该形态应删除或降级为「运行期数据盘唯一可行」。**
- ADR 0012 阶段 C「`install.sh --target asahi` 声明化」：被本篇第八节的 A1 取代——
  asahi 目标的落地形态是镜像 + 首启，而不是再加一个 install.sh 分支。

## 十、阶段 B 首次交叉审核（2026-11-23）

对「搬 UTM VM rootfs + 手工脚本装真机」这一方案做了五方向独立审核
（OpenRC / OpenZFS / Asahi+固件 / 参考实现对照 / 操作可行性），**全部判不通过**。
以下按「已修 / 待修」记录，供后续复用。

### 已修（payload 与脚本已更新）

| # | 问题 | 证据 | 修法 |
|---|---|---|---|

### 关键澄清（纠正先前判断）

- **黑屏 ≠ 固件缺失**：`appledrm.ko` 的 modinfo 无 `firmware=` 条目，官方 vendorfw 清单只有 Broadcom WiFi / 蓝牙 / ASMedia xHCI / 多点触控（M2）。黑屏应查 `appledrm` 是否加载 + Apple DTB 是否传到内核。
- **「一个镜像装多台」不是死结**：参考实现 `omarchy-mac-installer` 用镜像内固定 UUID + 首启取身份解决。ZFS GUID 冲突只在「同一台机同时看到两个同 GUID 池」时成立。
- **官方 installer 的 `UEFI environment only` 产物只有 `esp/m1n1/boot.bin`**，不写 `\EFI\BOOT\BOOTAA64.EFI`；所以第 2 段跑完后 ESP 上没有可引导对象，这正是必须用 live U 盘装 Ordo 并写 ZBM 的原因。

### 512 GB 外置盘的仓库制盘与回滚验收（2026-11-25）
